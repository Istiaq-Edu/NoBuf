H8: Fixed Reorder Coordinator to Break on ErrorDONE

What changed

In download_pool.rs, the reorder coordinator task now returns immediately after forwarding an error, instead of continuing to process chunks. Previously, if one worker errored, next_yield would get stuck at the gap and the stream would hang indefinitely.

Before:

Err(e) => {
    if tx_clone.send(Err(e)).is_err() { return; }
    // Continues processing — next_yield gets stuck
}

After:

Err(e) => {
    let _ = tx_clone.send(Err(e));
    return; // Break immediately — prevents hang
}

What you will see differently

No visible change for normal downloads — the fix only affects the error path. When a parallel download worker fails (network error), the download now stops cleanly instead of hanging forever.

How to test

  1. Download a file normally → should work as before
  2. If a download fails mid-way (e.g., network drops), the download should show an error and stop, not hang indefinitely
H10: Restricted CORS to Known Localhost OriginsDONE

What changed

Both servers (streaming on port 14201, REST API on configurable port) now restrict CORS to three specific origins instead of allow_any_origin(). Also removed allow_private_network_access() from the streaming server.

Allowed origins:

  • http://localhost:1420 (Vite dev server)
  • http://localhost:14200 (production localhost plugin)
  • http://nobuf-stream.localhost (custom protocol)

What you will see differently

  • Video streaming still works — the app's frontend is served from one of the allowed origins
  • External websites can no longer probe the servers — a malicious website visiting http://127.0.0.1:14201 will be blocked by CORS
  • REST API access from external websites is blocked — only the app's own frontend can call the API
Note: If you access the REST API from a tool like curl or Postman, it will still work (CORS only affects browsers, not CLI tools). If you access it from a browser-based tool on a different port, it may be blocked.

How to test

  1. Play a video → should stream normally (the frontend origin is allowed)
  2. Use the REST API from curl: curl -H "X-API-Key: *** http://127.0.0.1:8550/api/v1/health → should work (curl ignores CORS)
  3. Test CORS rejection: Open a browser, visit http://evil.com, open DevTools, run fetch('http://127.0.0.1:14201/stream/test') → should be blocked by CORS
H11: Hardcoded Remux Host (Removed Host Header Injection)DONE

What changed

The remux endpoint in server.rs no longer reads the Host HTTP header to construct the ffmpeg input URL. Instead, it hardcodes 127.0.0.1:STREAM_PORT. Previously, an attacker could set a malicious Host header to redirect ffmpeg to an external server, leaking the stream token.

Before:

let host = req.headers().get("host")...unwrap_or("127.0.0.1:14201");
input_source = format!("http://{}/stream/...", host);

After:

input_source = format!("http://127.0.0.1:{}/stream/...", crate::STREAM_PORT);

What you will see differently

No visible change — the remux feature (TS→MP4 fallback for playback) uses the same server as before. The only difference is that the server can no longer be tricked into connecting to an external server via a crafted Host header.

How to test

  1. Play a TS video file → if it uses the remux fallback, it should still work
  2. Test with malicious Host header: curl -H "Host: evil.com" http://127.0.0.1:14201/remux/... → ffmpeg should still connect to 127.0.0.1, not evil.com

H13: Added Path Validation to cmd_upload_fileDONE

What changed

cmd_upload_file now canonicalizes the file path and verifies it's a regular file before proceeding. Previously, any path string was accepted with zero validation, allowing a compromised webview to upload arbitrary local files (SSH keys, config files) to Telegram.

Added:

let canonical = std::fs::canonicalize(&path).map_err(|e| format!("Invalid path: {}", e))?;
if !canonical.is_file() {
    return Err("Path does not point to a regular file".to_string());
}

What you will see differently

  • Normal file uploads work fine — selecting a file via the dialog and uploading it works as before
  • Directory paths are rejected — if someone passes a directory path, they get "Path does not point to a regular file"
  • Non-existent paths are rejected — canonicalize fails with "Invalid path: ..."
  • Symlinks are resolved — canonicalize follows symlinks, so the real file is uploaded

How to test

  1. Normal upload: Click upload, select a file → should upload normally
  2. Invalid path (devtools): invoke('cmd_upload_file', { path: 'C:\\nonexistent' }) → should return "Invalid path" error
  3. Directory path: invoke('cmd_upload_file', { path: 'C:\\Windows' }) → should return "not a regular file" error

H18: Fixed cmd_zip_folder Symlink FollowingDONE

What changed

Added explicit .follow_links(false) to WalkDir::new() in cmd_zip_folder, plus an explicit symlink skip check. While the walkdir crate v2 defaults to not following symlinks, making this explicit prevents regressions if the default ever changes, and the symlink skip logs a warning for audit purposes.

Deferred Fixes — Why They Need More Work

H2: 29 (actually 12) production unwrap() on poisoned mutex

Why deferred: 12 .lock().unwrap() calls across 4 files (bandwidth.rs, auth.rs, lib.rs, stream_cache.rs). Each needs to be replaced with .lock().unwrap_or_else(|e| e.into_inner()) for poison recovery. Mechanical change but touches many files and needs careful testing to ensure poison recovery doesn't mask real errors.

Actual count from source verification: 12 occurrences (not 29 as originally reported). The audit overcounted by including semaphore .acquire().await.unwrap() calls, which are a different pattern (semaphore never closes in practice).

H3: DownloadPool bypasses rate limiter

Why deferred: The DownloadPool functions (sequential_stream, parallel_worker_stream, download_sub_range_iter) don't have access to rate_limiter — it's not passed as a parameter. Fixing this requires changing function signatures, which ripples through the call chain. The risk is moderate: DownloadPool is only used for file downloads (not streaming), and C3 (API semaphore) already fixed the more dangerous case.

H4 + H5: Accessibility + Test Coverage

Why deferred: These are large-scope items that need a dedicated development sprint:

  • H4: 0 aria-*, 0 role=, 0 aria-label in entire frontend. Adding accessibility requires touching nearly every component.
  • H5: useMSEPlayer.ts (5543 lines), FragmentStore.ts, ErrorBoundary.tsx, server.rs streaming logic, download_pool.rs — all have 0 tests. Writing tests for these is a multi-day effort.

H9: Proxy OOM (unbounded read_to_end)

Why deferred: The handle_nobuf_stream_protocol proxy in lib.rs:171-172 reads the entire response body into a Vec with no size limit. Fixing this requires forwarding Range headers from the incoming request to the upstream ureq request, plus adding a max body size check. This is a careful refactor of the proxy handler that needs thorough testing with video playback.

H17: DownloadPool worker session copies unencrypted

Why deferred: The DownloadPool creates 3 copies of the Telegram session file for parallel workers. All 4 copies (main + 3 workers) are unencrypted SQLite. Fixing this requires implementing session encryption at rest (e.g., using DPAPI on Windows or the keyring crate), which is an architectural change to the grammers session storage layer.

H19 + H20: Zip bomb protection + ZIP in-memory OOM

Why deferred: archive.rs downloads ZIP archives entirely into memory (Vec<u8>) with no size limit, no decompression ratio check, no max entry count. Fixing this requires refactoring the ZIP listing path to download to a temp file (like RAR/7z already do) and adding size/ratio/count limits. The _size variable from Telegram metadata is currently discarded — it should be checked before downloading.
