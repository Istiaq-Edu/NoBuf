Implemented Fixes — What Changed & How to Test

D01: Semaphore::new(2) — Enables Concurrent Streaming + Prebuffer

What changed: Changed Semaphore::new(1) to Semaphore::new(2) in lib.rs:253. The code had 4 comments across 2 files (mod.rs, server.rs) all saying "2 permits" — the code was wrong, the comments were right.

What you'll see differently: Proactive prebuffering works alongside streaming. Previously, if the proactive prebuffer held the only semaphore permit, /stream's fallback download would block until prebuffer released — causing 30s stalls. Now both can run concurrently (1 permit each), with the rate_limiter (Mutex<u64>) ensuring ≥250ms between API calls.

How to test:

  1. Play a video → streaming should work normally
  2. While streaming, the green prebuffer bar should also advance (proactive download running concurrently)
  3. No 30s stalls when both streaming and prebuffering are active

D02: Poison Recovery for 12 Mutex Locks

What changed: All 12 .lock().unwrap() calls on std::sync::Mutex in production code replaced with .lock().unwrap_or_else(|e| e.into_inner()). If a thread panics while holding a mutex, the mutex becomes "poisoned" — .unwrap() would panic again, cascading. unwrap_or_else recovers the data despite the poison.

Files changed: bandwidth.rs (6 sites), auth.rs (3 sites), lib.rs (2 sites), stream_cache.rs (1 site)

What you'll see differently: No visible change for normal operation. If a thread panics (e.g., grammers internal error), the app continues functioning instead of cascading into a full crash. The poisoned data may be stale, but the app stays alive.

How to test:

  1. Normal usage → bandwidth tracking, auth, streaming all work as before
  2. If a panic occurs (rare), the app should recover instead of crashing completely

D03: ConfigLock — Prevents TOCTOU Race

What changed: Added a ConfigLock (std::sync::Mutex<()>) as Tauri state. Both cmd_update_api_settings and cmd_regenerate_api_key now acquire this lock before doing their read-modify-write cycle on api_settings.json.

What you'll see differently: No visible change. If you rapidly toggle API settings and regenerate the key at the same time, both changes now persist correctly instead of one overwriting the other.

How to test:

  1. Open Settings → change API port → should save correctly
  2. Generate API key → should work, key persists
  3. Rapidly change settings + regenerate key → both should persist (previously, one could overwrite the other)

D07: FragmentStore LRU Eviction

What changed: Added MAX_CACHE_ENTRIES = 200 to FragmentStore. When the memory cache exceeds 200 entries, the oldest entry is evicted (JavaScript Map maintains insertion order, so keys().next().value gives the oldest key).

What you'll see differently: Reduced memory usage on long videos. Previously, the in-memory fragment cache grew unbounded — a 4GB video with 8MB fragments would accumulate 500+ entries (~4GB in RAM). Now it's capped at 200 entries (~1.6GB max). Evicted fragments are still in IndexedDB if needed.

How to test:

  1. Play a large video (>1GB) → should play without OOM
  2. Monitor memory in DevTools → should plateau around 200 fragments, not grow indefinitely
  3. Seeking backward to evicted ranges → should re-fetch from IndexedDB or backend (may have a slight delay)

D09: Typed Window Interface for __nobuf_* Globals

What changed: Created src/types/player-globals.d.ts with a typed Window interface declaring all 10 __nobuf_* properties. This provides compile-time type checking for the global state variables used by the streaming player.

What you'll see differently: No visible change. TypeScript now provides autocomplete and type checking for window.__nobuf_userSeekInProgress etc. A typo like __nobuf_userSeekInProgres would now be caught at compile time.

How to test:

  1. npx tsc --noEmit → should pass (no new type errors)
  2. Play a video → should work normally (the globals are still set/read at runtime)

D11: Reduced Shutdown Sleep from 2s to 500ms

What changed: The std::thread::sleep in the RunEvent::Exit handler reduced from 2000ms to 500ms. This sleep waits for Actix worker threads to drop file handles before cache cleanup. 500ms is sufficient — if it fails, the startup orphan cleanup catches it.

What you'll see differently: App closes 1.5 seconds faster. Previously, quitting the app had a 2-second delay; now it's 500ms. The improvement is most noticeable when closing the app while a video is streaming.

How to test:

  1. Stream a video, then close the app → should close noticeably faster than before
  2. Check that stream cache is still cleaned up (check %APPDATA%/com.istiaq.nobuf/stream-cache/ after exit)

D12: File Permissions on Config Files (Unix)

What changed: After atomic write of api_settings.json and network_settings.json, the files are now set to 0o600 (owner read/write only) on Unix systems. This prevents other users on the system from reading the API key hash or modifying network settings.

What you'll see differently: No visible change on Windows. On Linux/macOS, the config files are now only readable by the current user.

How to test:

  1. On Linux: change API settings → ls -la ~/.local/share/com.istiaq.nobuf/api_settings.json → should show -rw-------
  2. On Windows: no change (Windows uses ACLs, not Unix permissions)

Remaining Pending Tasks — Why They Need More Work

D04 (H3): DownloadPool Bypasses Rate Limiter

Why pending: The DownloadPool functions (sequential_stream, parallel_worker_stream, download_sub_range_iter) don't receive rate_limiter as a parameter. Adding it requires changing function signatures, which ripples through the call chain from fs.rs:923. The risk: if the throttle is too aggressive, file downloads become very slow. Needs runtime testing with concurrent streaming + file download.

D05 (H9+M3): Proxy OOM — Range Headers Not Forwarded

Why pending: The handle_nobuf_stream_protocol proxy in lib.rs:128-204 reads the entire response body into a Vec<u8> with no size limit. The fix requires: (1) forwarding Range headers from the incoming request to the upstream ureq request, (2) adding a max body size limit as defense-in-depth. This changes proxy behavior and needs careful testing with video playback through the nobuf-stream:// custom protocol.

D06 (H19+H20): Zip Bomb Protection + ZIP In-Memory OOM

Why pending: archive.rs downloads ZIP archives entirely into a Vec<u8> in memory with no size limit. A 2GB ZIP would consume 2GB of RAM. The fix requires: (1) checking the _size variable from Telegram metadata before downloading (currently discarded), (2) downloading to a temp file instead of memory (like RAR/7z already do), (3) adding MAX_ARCHIVE_SIZE, MAX_DECOMPRESSION_RATIO, and MAX_ENTRY_COUNT constants. This is a refactor of the ZIP branch that needs testing with various archive sizes.

D08 (M14): Sync Disk I/O in Async Path

Why pending: server.rs:1031-1054 performs synchronous std::fs::File::open + seek + read_exact inside an async stream. This blocks the Actix worker thread during disk reads. The fix is to wrap these in tokio::task::spawn_blocking, but this changes the streaming data flow and needs careful testing to ensure video playback still works smoothly.

D10 (H11): DownloadPool Workers Never Gracefully Shut Down

Why pending: The DownloadPool spawns 3 Tokio tasks for worker runners (download_pool.rs:66-71) but never stores the JoinHandles or sends a shutdown signal. On app exit, the tasks are killed when the Tokio runtime drops. The fix requires: (1) storing JoinHandles in the DownloadPool struct, (2) adding a shutdown() method that aborts the tasks, (3) calling it in the RunEvent::Exit handler before session cleanup. This changes the DownloadPool lifecycle and needs testing to ensure no session file corruption.

D13 (H4): Zero Accessibility Attributes

Why pending: The entire frontend has 0 aria-* attributes, 0 role= attributes, and 0 aria-label attributes. Screen reader users cannot navigate the app. Adding accessibility requires touching nearly every component — sidebar, file list, modals, buttons, video player. This is a multi-day effort that needs a dedicated sprint with accessibility testing tools (axe-core, NVDA).

D14 (H5): 0 Tests for Critical Modules

Why pending: useMSEPlayer.ts (5543 lines), FragmentStore.ts, ErrorBoundary.tsx, server.rs streaming logic, and download_pool.rs all have 0 tests. Writing tests for these is a multi-day effort. The most impactful tests would be: parse_range_header (server.rs), FragmentStore.mergeRanges, and the download_pool reorder coordinator.

D15 (H17): Session Encryption Research

Why pending: The Telegram session file is unencrypted SQLite. Encrypting it requires wrapping grammers_session::storages::SqliteSession with an encryption layer. Options: (1) Windows DPAPI via winapi crate, (2) cross-platform keyring crate for OS keychain access, (3) AES-256-GCM with user-derived key. Each option has tradeoffs and needs prototyping to verify grammers compatibility.

D16 (M15): 166 any Types in Frontend

Why pending: 119 of the 166 any types are in useMSEPlayer.ts alone. Many are for mpegts.js/mp4box internal APIs that don't have TypeScript declarations. Replacing them requires either writing .d.ts files for these libraries or using unknown with type guards. This is an incremental effort — start with the useRef<any> patterns (which can be useRef<unknown> or properly typed player interfaces).
