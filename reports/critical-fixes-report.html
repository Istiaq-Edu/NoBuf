What Changes You Will See

C1: SQLite Injection → Parameterized Queries CRITICAL FIX

What changed

All 7 SQL queries in folder_groups.rs that used format!() with manual .replace("'", "''") escaping have been replaced with parameterized queries using prepare() + bind().

Before (vulnerable):

conn.execute(format!("INSERT INTO groups (name, color_hex, display_order) VALUES ('{}', '{}', {})",
    name.replace("'", "''"), color_hex.replace("'", "''"), max_order + 1))

After (safe):

let mut stmt = conn.prepare("INSERT INTO groups (name, color_hex, display_order) VALUES (?, ?, ?)")?;
stmt.bind((1, name.as_str()))?;
stmt.bind((2, color_hex.as_str()))?;
stmt.bind((3, max_order + 1))?;
stmt.iter().next();

What you will see differently

  • No visible UI change — folder group creation, renaming, deletion, and assignment all work exactly the same
  • Group names with special characters (quotes, semicolons, SQL keywords) are now stored literally instead of potentially causing errors or injection
  • Error messages may differ slightly — if a database error occurs, the message comes from SQLite directly instead of from a format!() string

How to test it

  1. Create a group with a quote in the name: Open Settings → create a new group, name it O'Brien's Files → verify it saves and displays correctly
  2. Create a group with SQL-like name: Name a group test'; DROP TABLE groups;-- → verify it saves literally (the name should appear exactly as typed), and the groups table is NOT dropped
  3. Rename a group with special chars: Rename any group to It's a "test" → verify the rename succeeds
  4. Delete and reassign: Delete a group, verify folders assigned to it show "no group", reassign a folder to another group → verify it works
  5. Reorder groups: Drag groups to reorder → verify order persists after app restart
C2: SSRF → URL Validation + Filename Sanitization CRITICAL FIX

What changed

Two new functions added to fs.rs: validate_url() and sanitise_filename(). The cmd_upload_from_url function now validates the URL before fetching and sanitizes the filename before writing to disk.

URL validation blocks:

  • Non-HTTP(S) schemes (file://, ftp://, gopher://)
  • Loopback IPs (127.0.0.1, ::1)
  • Private IPs (10.x, 172.16-31.x, 192.168.x)
  • Link-local IPs (169.254.x — cloud metadata endpoints)
  • Unspecified IPs (0.0.0.0)
  • Blocked hostnames (localhost, 169.254.169.254, metadata.google.internal)

Filename sanitization removes:

  • Path traversal sequences (../../) — extracts only the file name component
  • Control characters and null bytes
  • Windows reserved characters (: < > " | ? *)

What you will see differently

  • Remote upload from valid URLs still works — https://example.com/file.zip uploads normally
  • Remote upload from internal URLs is rejected — http://127.0.0.1:8550/api/v1/files shows error: "URLs pointing to internal addresses are not allowed"
  • Remote upload from cloud metadata is rejected — http://169.254.169.254/... shows the same error
  • Filenames with path traversal are sanitized — a server sending Content-Disposition: filename="../../evil.exe" will result in the file being saved as evil.exe inside the temp directory, not outside it
  • New dependency — url = "2" added to Cargo.toml (adds ~50KB to binary)

How to test it

  1. Valid upload: Click the globe icon (Remote Upload), enter https://example.com/test.txt → should download and upload normally
  2. SSRF blocked: Enter http://127.0.0.1:8550/api/v1/files → should show error "URLs pointing to internal addresses are not allowed"
  3. Cloud metadata blocked: Enter http://169.254.169.254/latest/meta-data/ → same error
  4. Non-HTTP blocked: Enter file:///C:/Windows/System32/cmd.exe → should show error "Only HTTP(S) URLs are allowed"
  5. Filename sanitization: If you control a test server, send Content-Disposition: attachment; filename="../../test.txt" → verify the file is saved inside the temp directory, not outside
C3: Missing Semaphore → Added to API Download Loop CRITICAL FIX

What changed

The REST API file download endpoint in api_routes.rs was the ONLY download path in the entire codebase that did not use the download semaphore or rate limiter. This would trigger FLOOD_PREMIUM_WAIT on Telegram when downloading files via the REST API, which would stall ALL downloads (including active video streams) for 300+ seconds.

Added download_semaphore.acquire() + throttle_api_calls() + yield_now() — the same pattern used by all 10 other download paths in the codebase.

What you will see differently

  • API downloads are now slower but safe — downloads via the REST API will be rate-limited (same as streaming), preventing Telegram FLOOD_WAIT bans
  • No more FLOOD_WAIT when using API + streaming simultaneously — previously, downloading a file via API while streaming video could trigger a flood wait that killed both
  • No visible UI change — the REST API is used by external integrations, not the main UI

How to test it

  1. Enable the REST API: Settings → toggle API on, generate an API key
  2. Download a file via API: curl -H "X-API-Key: YOUR_KEY" http://127.0.0.1:8550/api/v1/files/123/download -o test.bin → should download successfully
  3. Stream + API download simultaneously: Start streaming a video in the app, then download another file via API → both should work without FLOOD_WAIT errors
  4. Check logs: Look for absence of "FLOOD_WAIT" errors in the console during API downloads
C4: RAR Path Traversal → Post-Extraction Validation CRITICAL FIX

What changed

When viewing a RAR archive, the app previously called extract_all() which writes files using their raw archive names — if a RAR contains an entry named ../../Windows/System32/evil.dll, the file would be written outside the extract directory. Now, after extraction, the app verifies every extracted file's canonical path is within the extract directory. If any file escaped, the operation is rejected and cleaned up.

What you will see differently

  • Normal RAR files work fine — viewing a regular RAR archive shows the file list as before
  • Malicious RAR files are rejected — a RAR with path traversal entries shows error: "Archive contains path traversal entry: '...'"
  • No files written outside temp directory — even if extraction starts, the validation catches any escaped files and cleans up
Note: This is a validation-based fix, not a prevention-based fix. The RAR is still extracted to disk before the check runs. A future improvement should replace the rar crate with unrar which supports list-only mode (no extraction needed for listing). But the current fix prevents any files from persisting outside the temp directory.

How to test it

  1. View a normal RAR: Upload a .rar file to a Telegram folder, right-click → "View Archive" → should show file list normally
  2. View a malicious RAR (if you can create one): Create a RAR with an entry named ../../../test.txt, upload it, view it → should show error "Archive contains path traversal entry"
  3. Verify no files outside temp: After viewing any RAR, check %TEMP%\nobuf_archive_rar\ → should be cleaned up
  4. ZIP and 7Z still work: View .zip and .7z files → should work normally (they were not affected by this bug)
C5: shell:allow-open → Removed + Custom Safe Command CRITICAL FIX

What changed

The shell:allow-open permission was removed from capabilities. This permission allowed the webview to open ANY URI scheme (file://, smb://, https://) via the OS default handler. A compromised webview could open file:///C:/Windows/System32/cmd.exe or smb://attacker.com/share (NTLM hash leak).

Replaced with a custom cmd_open_url Tauri command that validates the URL is HTTP(S) before opening. The AuthWizard's "Visit my.telegram.org" links now use this safe command.

What you will see differently

  • "Visit my.telegram.org" links still work — clicking the link in the auth wizard opens your browser to https://my.telegram.org
  • Non-HTTP URLs are rejected — if a compromised webview tries to open file:// or smb://, it gets error "Only HTTP(S) URLs can be opened"
  • No shell permission in capabilities — the app has one less dangerous permission

How to test it

  1. Test the auth link: On the setup screen (before login), click "my.telegram.org" → should open your browser to https://my.telegram.org
  2. Test the button link: Click the "Go to Telegram's Developer Portal" button → should open browser
  3. Test rejection (devtools): Open DevTools console, run await __TAURI_INTERNALS__.invoke('cmd_open_url', { url: 'file:///C:/test' }) → should return error "Only HTTP(S) URLs can be opened"
C6: ffmpeg Auto-Download → Removed CRITICAL FIX

What changed

The ffmpeg_sidecar::download::auto_download() call was removed from sprite.rs. Previously, if ffmpeg was not found on the system, the app would automatically download a pre-built binary from the internet with no checksum verification — a MITM attacker could replace it with malware (RCE). Now, if ffmpeg is not found, the app returns a clear error message directing the user to install ffmpeg manually.

What you will see differently

  • If you have ffmpeg installed: No change — sprite sheet generation and video duration probing work normally
  • If you do NOT have ffmpeg installed: Instead of auto-downloading, you will see error: "ffmpeg not found. Install ffmpeg and add it to PATH." (or "place ffmpeg.exe next to the app executable")
  • No silent network requests — the app no longer makes any download request when ffmpeg is missing

How to test it

  1. With ffmpeg on PATH: Hover over a video file → sprite thumbnails should generate normally
  2. Without ffmpeg: Rename/remove ffmpeg from PATH, restart app, hover over a video → should show error, NOT download anything
  3. Check network tab: Open DevTools Network tab, trigger sprite generation without ffmpeg → should see NO network request to github.com or any download URL
  4. Manual ffmpeg: Place ffmpeg.exe next to the app executable → sprite generation should work
C7: unpkg CDN Load → Removed CRITICAL FIX

What changed

The fallback code in MP4Player.ts that loaded mp4box from https://unpkg.com/mp4box@0.5.2/dist/mp4box.all.js with no integrity hash was removed. This was a supply chain risk — a compromised unpkg.com could deliver malicious JavaScript that executes in the WebView with full Tauri IPC access (RCE). The primary import('mp4box') path (bundled by Vite) is the correct one.

What you will see differently

  • MP4 video playback works normally — mp4box is bundled by Vite and loaded from the local bundle, not a CDN
  • No network request to unpkg.com — even if the bundled import fails, the app throws an error instead of fetching from the internet
  • If mp4box somehow fails to load: You will see error "mp4box module not available — ensure it is installed and bundled by Vite" instead of a silent CDN load

How to test it

  1. Play an MP4 video: Click on any .mp4 file in the file explorer → should play normally in the media player
  2. Check network tab: Open DevTools Network tab, play an MP4 → should see NO request to unpkg.com or any CDN
  3. Check console: No errors should appear in the console during MP4 playback

After building and launching the app with all fixes applied, do these 5 things to verify nothing is broken:

  1. Play a video — click any .mp4 or .ts file → should play normally (C3, C7)
  2. Create a folder group — Settings → create a group named Test "Group" → should save and display (C1)
  3. Click the my.telegram.org link — on the auth screen → should open browser (C5)
  4. Upload from URL — enter a valid https URL → should download and upload (C2)
  5. View a ZIP archive — right-click a .zip file → "View Archive" → should show file list (C4)

If all 5 work, the critical fixes have not broken any existing functionality.
