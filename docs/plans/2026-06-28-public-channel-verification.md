## P0 — Runtime Blockers (Must Fix Before Testing)

### V1: Add 10 new commands to `build.rs` codegen list
**Problem:** `build.rs` has an explicit command list for Tauri permission codegen. Our 10 new commands are NOT listed → no permission `.toml` files are generated → `invoke()` calls from frontend will be **denied at runtime**.
**Evidence:** `ls app/src-tauri/permissions/autogenerated/ | grep public` returns nothing. `capabilities/default.json` has no `allow-cmd-*` entries for new commands.
**Fix:**
- Add these 10 commands to `build.rs` after `"cmd_open_url",`:
  ```
  "cmd_resolve_channel_link",
  "cmd_join_channel_by_link",
  "cmd_list_joined_channels",
  "cmd_add_joined_channel",
  "cmd_get_public_channels",
  "cmd_get_public_channel_files",
  "cmd_remove_public_channel",
  "cmd_forward_to_folder",
  "cmd_update_nb_pub_sync",
  "cmd_sync_public_channels",
  ```
- Run `cargo build` to auto-generate permission files
- Add `allow-cmd-*` entries to `capabilities/default.json` for all 10
**Verify:** `npm run tauri dev` → add a channel → no permission denied error in console

### V2: SQL injection via `format!()` on INSERT statements
**Problem:** 4 INSERT statements use `format!()` with string interpolation for `name` and `username` fields. While `.replace("'", "''")` provides basic escaping, it's not bulletproof and is a bad pattern.
**Evidence:** Lines 333, 463, 711, 973 in `public_channels.rs` use `format!("INSERT INTO ... VALUES ({}, '{}', ...")` with channel title/username interpolated.
**Fix:** Convert all INSERT/UPDATE statements to use parameterized queries with `stmt.bind()` instead of `format!()`. The deduplication SELECT already uses `stmt.bind()` — follow that pattern.
**Verify:** `cargo check` passes. Try adding a channel with `'` in its name — no SQL error.

### V3: `upload_file` error mapping
**Problem:** `client.upload_file()` returns `Result<Uploaded, io::Error>`. We use `.map_err(map_error)?` but `map_error` looks for "FLOOD_WAIT" in the error string — `io::Error` will never contain that, so FLOOD_WAIT detection is dead code for this call. More importantly, `io::Error` messages are generic ("No such file or directory") and don't help the user.
**Fix:** Change to `.map_err(|e| format!("Failed to upload sync file: {}", e))?` for clearer error messages.
**Verify:** `cargo check` passes.

## P1 — Correctness Issues (Should Fix Before Release)

### V4: Rename button visible for public channels
**Problem:** ContextMenu's Rename button is always shown (hardcoded `disabled`). For public channels it should be hidden entirely, like the Delete button is wrapped with `!showForwardOption`.
**Evidence:** `ContextMenu.tsx` line 129: `<button disabled className=...>` — always rendered.
**Fix:** Wrap Rename button with `{!showForwardOption && (...)}`.
**Verify:** Right-click a file in a public channel → no Rename button visible.

### V5: `set_setting` uses `format!()` with string interpolation
**Problem:** `set_setting()` in `public_channels.rs` builds SQL with `format!()` interpolating key and value. Keys are hardcoded ("nb_pub_channel_id", "nb_pub_message_id") so not user input, but it's still a bad pattern.
**Fix:** Convert to parameterized query with `stmt.bind()`.
**Verify:** `cargo check` passes.

### V6: `get_setting` swallows errors silently
**Problem:** `get_setting()` uses `.ok()?` on every step — connection errors, SQL errors, and bind errors are all silently ignored, returning `None`. This means a corrupted DB would silently lose the [NB-PUB] channel ID and trigger unnecessary channel creation.
**Fix:** At minimum, log errors before returning `None`. Better: return `Result<Option<String>, String>` and propagate.
**Verify:** `cargo check` passes. Check logs when DB has issues.

### V7: Sync JSON download has no retry
**Problem:** The `iter_download` loop in `cmd_sync_public_channels` has no retry on FLOOD_WAIT or network errors. A single FLOOD_WAIT during sync kills the entire sync operation. The sync file is small (~1KB) so this is unlikely, but follows the pattern from the skill memory: "Any long-running Telegram download task MUST have retry+backoff."
**Fix:** Add 3-retry with exponential backoff (2s→4s→8s) around the download loop.
**Verify:** `cargo check` passes. Code review.

### V8: `cmd_update_nb_pub_sync` called without error handling in frontend
**Problem:** In `usePublicChannels.ts`, `invoke('cmd_update_nb_pub_sync').catch(() => {})` silently swallows ALL errors. If the sync update fails (network, FLOOD_WAIT, [NB-PUB] channel deleted), the user has no idea their changes aren't synced to other devices.
**Fix:** At minimum, log the error. Better: show a non-intrusive toast: "Sync update failed — changes are local only."
**Verify:** Code review. Check console when sync fails.

### V9: Missing `useEffect` import in FileExplorer
**Problem:** The infinite scroll `IntersectionObserver` uses `useEffect` and `useRef`. If these aren't imported from React, the component will crash at runtime.
**Evidence:** Need to verify FileExplorer.tsx has `useEffect, useRef` in its React imports.
**Fix:** Check and add missing imports if needed.
**Verify:** `tsc --noEmit` should catch this. But verify manually.

### V10: `channelIsPublic` prop on ContextMenu conflicts with `showForwardOption`
**Problem:** ContextMenu has both `channelIsPublic` (for Copy Link button) and `showForwardOption` (for Forward button). These overlap — a public channel should show both Copy Link and Forward, but the logic might be inconsistent.
**Fix:** Audit that `channelIsPublic` is passed correctly from Dashboard for public channels (it controls whether Copy Telegram Link is enabled).
**Verify:** Right-click in a public channel → Copy Link enabled, Forward visible, Delete hidden.

## P2 — Optimizations & Code Quality

### O1: Remove unused imports in `public_channels.rs`
**Problem:** 4 unused imports generate warnings: `Serialize`, `Deserialize`, `HashMap`, `Arc`, `RwLock`.
**Fix:** Remove unused `use` statements. Run `cargo fix --lib -p app` or manually remove.
**Verify:** `cargo check` — zero warnings from `public_channels.rs`.

### O2: Deduplicate `ResolveUsername` + `JoinChannel` in `cmd_join_channel_by_link`
**Problem:** For public channels, we call `ResolveUsername` to get `access_hash`, then immediately call `JoinChannel` with it. This is 2 API calls. We could use `ResolveUsername`'s returned `Peer` directly in `JoinChannel` without a second round trip — but `JoinChannel` takes `InputChannel`, not `Peer`, so we need the `access_hash` from `ResolveUsername` anyway. The 2-call pattern is correct.
**Decision:** No change needed — the 2-call pattern is correct.

### O3: Cache `iter_dialogs` results across commands
**Problem:** Multiple commands (`cmd_list_joined_channels`, `cmd_add_joined_channel`, `find_or_create_nb_pub_channel`, `get_nb_pub_access_hash`, `cmd_sync_public_channels`) each scan `iter_dialogs()` independently. For users with many dialogs, this is slow.
**Fix:** Consider a one-time dialog scan on startup that populates the peer cache, then all subsequent commands use the cache. This is an architectural change — defer to a future optimization sprint.
**Decision:** Defer — current behavior is correct, just not optimal.

### O4: `PublicChannel` serialization for sync JSON
**Problem:** `PublicChannel` has `Serialize`/`Deserialize` derives — confirmed correct. But `serde_json::to_string()` will serialize ALL fields including `is_member` and `access_hash`. The `access_hash` is sensitive (it's a Telegram auth token) — storing it in a channel message is a minor security concern.
**Fix:** Add `#[serde(skip_serializing)]` to `is_member` and use `#[serde(rename = "ah")]` for `access_hash` to obscure it slightly. OR accept the risk since the [NB-PUB] channel is private (only the user can access it).
**Decision:** Accept — [NB-PUB] is a private channel only the user can access. No change needed.

### O5: Frontend — `loadMore` mutation doesn't show loading state
**Problem:** When infinite scroll triggers `loadMore.mutate()`, there's no visual indicator that more files are loading beyond the "Loading more..." sentinel. If the request is slow, the user sees the sentinel but no spinner.
**Fix:** Add `loadMore.isPending` check to show a spinner in the sentinel div.
**Verify:** Visual test with a large channel.

### O6: Frontend — `pubChannelsLoading` unused
**Problem:** `usePublicChannels()` returns `isLoading` but it's destructured as `pubChannelsLoading` in Dashboard and never used in the UI.
**Fix:** Either use it for a loading spinner in the sidebar, or remove it to avoid dead code.
**Verify:** `tsc --noEmit` — no unused variable warning.

### O7: Frontend — Remove button on PublicChannelItem calls `onSelect` instead of `onRemove`
**Problem:** In `PublicChannelSidebarSection.tsx`, the `PublicChannelItem`'s `onRemove` callback should call the `onRemove` prop (which calls `handleRemovePublicChannel`), not `onSelect`. Need to verify this was wired correctly by Task 20+21.
**Evidence:** Line 57-59 of `PublicChannelSidebarSection.tsx` checks `if (onRemove) { onRemove(channel.channel_id); }` — looks correct.
**Decision:** No change needed — already fixed.
