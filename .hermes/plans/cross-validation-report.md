# Cross-Validation Report — Universal Transcode Tier plan

Method: re-derived every load-bearing claim in `universal-transcode-tier.md` against
source (server.rs, useMSEPlayer.ts) and against **execution** on real ffmpeg with
synthetic clips matching the Panchayat file (10-bit HEVC Main10 + E-AC-3 5.1).
Prior diagnosis treated as hypothesis. Marked VERIFIED / FALSIFIED / INCONCLUSIVE.

Machine: i9-13900H, ffmpeg with h264_qsv / h264_nvenc / h264_amf / libx264.

---

## C1 — "10-bit HEVC is the video blocker; hvc1.2.1.L120 = Main 10 (10-bit)"
**VERIFIED.** Log: `addSourceBuffer('video/mp4;codecs=hvc1.2.1.L120.B0') unsupported`.
`.2.1` profile field = 2 = HEVC Main 10. Synthetic clip probe: `profile=Main 10`,
`pix_fmt=yuv420p10le`. Filename confirms `10bit ... x265 HEVC`.

## C2 — "10-bit SDR, not HDR; route by color metadata not bit depth"
**VERIFIED.** Synthetic 10-bit clip: `color_transfer=None`, `color_primaries=None`
→ SDR. True-HDR clip built separately probes `transfer=smpte2084 primaries=bt2020`.
The two are distinguishable → gate on transfer/primaries is sound.

## C3 — "Detect HDR client-side with mediabunny"
**FALSIFIED.** mediabunny 1.45.4 `getColorSpace()` on the true-HDR clip returned only
`matrix: bt2020-ncl` — **no `transfer`, no `primaries`**. Transfer (smpte2084/HLG) is
the definitive HDR marker and mediabunny does not surface it from the container header.
Stream-level ffprobe ALSO missed it (`color_transfer` absent at stream level).
→ **HDR detection MUST be backend, FRAME-level ffprobe.** (see C4)

## C4 — "Frame-level ffprobe reads HDR reliably"
**VERIFIED.** `ffprobe -show_frames -read_intervals %+#1` on HDR clip returned
`color_primaries=bt2020, color_transfer=smpte2084, color_space=bt2020nc` from the
bitstream VUI. This is the authoritative detection method. Container/stream-level
do NOT suffice.

## C5 — "Add is_hdr/needs_transcode to Fmp4MetadataResponse; frontend preflights it" (plan items 5-6-7)
**FALSIFIED — ARCHITECTURAL.** `/fmp4/metadata` (server.rs:3449) does **NOT run
ffprobe**. It reads the TS stream cache and feeds the custom Rust `TsDemuxer`
(3559-3569). For MKV that demuxer cannot parse Matroska — which is exactly why the
original log shows `[FMP4-META] using AVC default`. Adding HDR/transcode fields there
would leave them unpopulated (or wrong) for MKV.
→ The probe that CAN classify (ffprobe) lives ONLY inside `/remux` (server.rs:2099).
→ **Correction:** the transcode/HDR decision must be made where ffprobe runs — inside
`/remux` — OR a NEW dedicated probe endpoint must be added that runs ffprobe on MKV.
The plan's "reuse Fmp4MetadataResponse" is invalid.

## C6 — "eac3->aac fix resolves the muxer crash" (plan item 4/3)
**INCONCLUSIVE — cannot claim resolved.** The real crash occurred in **Strategy B
(piped)**, which per source (server.rs:2312-2341) ALREADY CONTAINS the fix
(`-avoid_negative_ts make_zero`, `-af asetpts=N/SR/TB`, `-max_interleave_delta 0`).
The file crashed **despite** the fix present. My synthetic 5.1 eac3 clip run through
the EXACT Strategy B args produced clean output (exit 0, no muxer error) — i.e. the
synthetic clip does NOT reproduce the crash.
Difference: real input was a **live uncached HTTP stream** (`/stream/...` served from
Telegram poll, possible byte gaps/partial data at ffmpeg read time), not a clean file.
→ Root cause of the real EINVAL is **NOT proven**. It may be input-starvation / partial
stream data, not timestamp geometry. Needs reproduction against the live stream path.
Strategy A (disk, 2187-2206) genuinely LACKS the fix — that patch is still valid, but
it is not proven to be the crash cause.

→ Plan must specify a VERIFIED QSV invocation, not the hwupload chain. libx264

   endpoint never ffprobes MKV. Either decide inside `/remux`, or add a NEW ffprobe
   preflight endpoint. Re-architect items 5/6/7.
2. **C3:** Drop client-side mediabunny HDR detection entirely — it can't read transfer.
3. **C6:** Do not claim the eac3 fix resolves the crash. The crash reproduced on the
   LIVE STREAM input despite the fix already being present in Strategy B. Must reproduce
   against `/stream` input before claiming a fix. Strategy-A patch is still worth doing
   but is not the proven cause.
4. **C7:** Replace the `hwupload` QSV chain with verified Variant A or B.
5. **C8:** Don't quote a realtime multiple as fact until hand-test.

## Internet-sourced verification (external authorities)

### E1 — hvc1.2.1.L120 = Main 10, Level 4 (codec-string semantics)
**VERIFIED** vs Wikipedia HEVC tiers/levels + DICOM spec + ISO codec-string refs.
`.2` = profile 2 = Main 10; `L120` = level 120/30 = Level 4; `B0` = Main tier.
Confirms C1 independently.

### E2 — Chromium/WebView2 MSE + HEVC (chromium issue 40406706, StaZhu guide 1.4k★)
**KEY NUANCE — refines the whole approach.** Chromium's own tracker historically said
"no plans to support HEVC in Chrome" for MSE, BUT the StaZhu hardware-decode guide
(authoritative, continuously updated) documents that Chrome/Edge on Windows **do**
support HEVC **Main 10 / 10-bit 4:2:0 hardware decode** via File + **Media Source
Extensions** + WebCodecs — **conditional on the platform HEVC decoder being present**.
On Windows that decoder = the Microsoft Store "HEVC Video Extensions". The app's own
code already knows this (useMSEPlayer.ts:5813 tells the user to install it for $0.99).
→ Implication: whether HEVC (8-bit OR 10-bit) plays via MSE/native on THIS machine is a
  **machine-state variable** (is the HEVC extension installed?) that I have NOT verified.
  If installed, 10-bit Main10 could play natively with zero transcode. If not, nothing
  HEVC plays without transcode. The transcode tier is the correct **extension-independent**
  guarantee, but "must transcode" is only strictly true when the extension is absent.

### E3 — HDR→native is SOUND on this platform (StaZhu HDR table)
**VERIFIED + REINFORCES the HDR routing decision.** Chrome/Edge on Windows support
PQ, HDR10, and HLG with automatic tone-mapping from static metadata. So routing true
HDR (bt2020+PQ/HLG) to native `<video>` will actually render correctly on Edge/WebView2
— the earlier worry that native HDR might look wrong is unfounded for PQ/HDR10/HLG.
EXCEPTION: **Dolby Vision Profile 5 is ❌ unsupported** (only DV P8.1/P8.4 cross-compat
work). DV P5 files routed to native would fail → those still need transcode. Refines C2:
HDR→native is right for HDR10/HLG, but DV P5 is a carve-out that must still transcode.

### E4 — QSV texture error 80070057 (Intel forums / ffmpeg trac)
**CONSISTENT.** `80070057 = E_INVALIDARG` from D3D11. Known with `hwupload` when the
frame context format doesn't match the QSV device on 10-bit→8-bit conversions. Corroborates
C7: use `vpp_qsv=format=nv12` (Variant A) or sw-decode→qsv (Variant B), not raw hwupload.

## Net additions from external verification
6. **E2:** Before committing to always-transcode HEVC, the plan should PROBE whether the
   Windows HEVC Video Extension is installed (native `canPlayType('video/mp4;codecs=hvc1...')`
   returns 'probably'/'maybe' when present — the code already checks this at 5796). If
   present, 8-bit HEVC can stay on the cheap native/copy path; only 10-bit-via-MSE and
   truly-unsupported cases transcode. This avoids needless GPU load on machines that can
   already decode HEVC.
7. **E3:** Add a Dolby Vision Profile 5 carve-out — DV P5 must transcode even though it's
   "HDR", because native can't render it. Detect via ffprobe side_data / dovi config.

### PROBE 2 — reproduce the eac3 EINVAL against live-stream input → **NOT REPRODUCED**
Ran the EXACT Strategy B args (server.rs:2312-2341) against, in escalating fidelity:
  - 2a: clean local file → exit 0, no muxer error
  - 2b: clean HTTP input (localhost server) → exit 0
  - 2c: identical stream layout to real REMUX-PROBE (idx0 hevc, idx1 eac3) → exit 0
  - 2d: THROTTLED/trickled HTTP (150ms stalls every 256KB, mimics Telegram poll
    starvation) → exit 0, out=8.5MB, no EINVAL
**None reproduce the crash.** Trigger is NOT: timestamp geometry, HTTP transport, stream

→ Remaining untested variable: the **real DDP 5.1 bitstream structure**. Amazon DDP tracks
  carry E-AC-3 **dependent substreams (JOC/Atmos extension)**; ffmpeg's own `eac3` encoder
  CANNOT produce that substream structure (confirmed: synthetic clip profile=unknown, no
  substreams). The real crash likely comes from the aac ENCODER choking on decoded frames
  from a dependent-substream eac3 source, or a channel-layout mismatch (6 ch + LFE geometry)
  — NOT from muxer timestamps.
→ **Actionable correction:** the fix is almost certainly NOT more timestamp flags. Candidates
  to test against a REAL DDP file (cannot synthesize locally):
    (a) `-c:a ac3` instead of aac (AC-3 is natively MPEG-TS-muxable, no re-encode geometry issues), or
    (b) explicit `-ac 6 -channel_layout 5.1` / downmix `-ac 2`, or
    (c) drop the dependent substream on decode.
  This MUST be validated on the actual Panchayat file — my synthetic eac3 is not
  representative. Do NOT ship a speculative eac3 fix.
